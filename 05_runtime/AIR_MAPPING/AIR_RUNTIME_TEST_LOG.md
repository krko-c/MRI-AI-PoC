## 2026-09-14 — 설계 결정: 소스 라우팅은 사전 지식이 아니라 재시도로 푼다

## 2026-09-14 — 화면 출력이 한 덩어리로 뭉치는 문제

사용자 지적: 최종 산출물인데 읽기가 어렵다. 이전 버전 화면과 비교해 보여 주었다.

**원인은 양식이 평문 고정폭으로 설계되어 있는데 화면은 마크다운으로 렌더된다는 것이다.**
마크다운은 **한 줄 줄바꿈과 앞 공백을 버린다.** 그래서

- 03X 요약표의 공백 정렬 칸(`ID   No   이슈 … 상품 테마 고객`)이 무너진다
- `==========` 구분선과 들여쓰기가 사라진다
- `판정  MONITOR   조사권고 —   원문 정합성 PASS` 의 칸 간격이 한 칸으로 줄어든다
- 노드 10 의 `□` / `○` / `-` 계층이 줄바꿈을 잃고 한 문단으로 뭉친다

앞서 고친 물결표 취소선과 같은 뿌리다. **양식을 평문으로 쓰고 마크다운으로 렌더했다.**

**수정 — 에이전트2 노드 10**

「화면 출력」 1) 을 "평문 그대로 유지, 마크다운 금지" 에서
"계층만 마크다운으로 옮긴다"로 바꿨다. 평문 ↔ 화면 대응을 표로 명시:
`<#번호 주제명>` → `##`, `□ 대제목` → `### □ …`(기호 유지),
`○ 주요 항목` → `**○ …**` 한 줄 + 앞뒤 빈 줄, `- 세부 항목` → 마크다운 목록.

**`final_report_text` 필드 자체는 평문으로 그대로 둔다.** 그쪽은 한글문서에 붙여 넣는 값이다.
마크다운은 화면에만 적용한다. 같은 내용이 두 표기로 나가는 것이 아니라,
JSON 은 붙여넣기용 · 화면은 읽기용으로 역할이 갈린다.

**수정 — 에이전트1 03X**

- 1) 스크리닝 요약표: 공백 정렬 표 → **마크다운 표**. 판정 의미 3줄 → 불릿.
- 2) 이슈별 검토서: `=====` 구분선 → `---`,
  `[S04] #4 제목` → `### [S04] #4 제목`,
  판정·렌즈 줄 → `**판정** MONITOR · **조사권고** —` 형태,
  `□ 소제목` → `**□ 소제목**` + 빈 줄 + 마크다운 목록,
  렌즈별 평가 → `- **상품 2점** — 사유` 목록.

검토서는 화면 전용이라(JSON 에 대응 필드가 없다) 마크다운으로 직접 바꿨다.

**에이전트1 고정 원칙과의 관계.** 이 변경은 handoff JSON 계약을 건드리지 않는다.
바뀌는 것은 사람이 읽는 화면뿐이라 에이전트2 시험의 변수가 되지 않는다.

## 2026-09-15 — 출처 표시: 보고서에서 근거를 확인할 수 있게 한다

사용자 지적: 결과 보고를 읽어도 **근거가 있는지 지어낸 것인지 판단이 안 된다.**
JSON 이 그 역할을 해야 할 텐데 도움이 안 되고, 요즘 AI 검색은 본문을 다 연결해 준다.

**`source_path` 와 도구가 돌려준 원문을 버린다.** 그래서 10 이 보고서를 쓸 때
인용할 원문 자체를 갖고 있지 않다. 본문에는 표시가 없고, JSON 에는 파일명뿐이다.

어떤 문장을 확인하려면 본문 → 어느 근거인지 추측 → JSON 에서 E0x 찾기 →
파일명 확인 → 그래도 원문은 없음. 사실상 확인 불가능이다.

**수정 1 — 07 이 경로와 원문을 들고 온다**

evidence item 에 두 필드 추가.
- `source_paths` — 검색 결과의 `source_path` 그대로. `documents/upload/kb-` 형식이 아니면
  **그 근거는 VERIFIED 가 될 수 없다.** `DATA_GAP` 으로 내리고 사유를 `limitations` 에 적는다.
- `verbatim_quotes` — 주장을 뒷받침하는 도구 출력 문장 1–2개를 **그대로**. 요약·윤문 금지.
  **인용을 만들 수 없으면 VERIFIED 가 아니다.** 검색 결과에 그 문장이 없다는 뜻이다.
  (INFERENCE 는 예외 — 추론의 출발점이 된 사실을 인용한다.)

**수정 2 — 10 이 본문에 근거 번호를 달고 끝에 근거 절을 낸다**

- 「(현황)」 세부 불릿 끝에 `[E02]`. 여럿이면 `[E02·E04]`.

  「추가 확인사항」으로 옮긴다.
- 「핵심 판단」·「계획」에는 달지 않는다. 판단과 제안이지 사실 진술이 아니다.
- 보고서 맨 끝 `## 근거` 절:

      **[E02]** 확인 · `08_주식보상_2조2811억_RSU확산.txt`
      > 2026년 1~5월 시가총액 100대 기업 중 18개사가 … 3.3배 증가한 수치이다.

결정적으로 06E2 는 **06E 가 지어낸 파일명에 `_세부` 를 붙여 속편을 만들었다.**

**보고서 기준으로 근거 19건 중 7건이 날조다.
「(현황) 정책·제도」 블록은 문단 4개 전부가 지어낸 것이다.**

### 진단 — 여섯 번째 회피 형태: 검사 항목을 충족시켜 검사를 무력화한다

지금까지 관찰된 순서다.

| 실행 | 같은 태스크(S06-T01)의 결과 |
|---|---|
| 2·3차 | 정직한 `NO_RESULT`. KB 가 "없다"고 답한 문장까지 인용 |
| 4차 | 지어낸 `SUCCESS`. `source_path` = "법제처 상법 개정 공포문" (탐색 경로 문자열) |
| **5차** | **지어낸 `SUCCESS`. `source_path` = `documents/upload/kb-66cbc0fb/*.pdf`** |

규칙을 조일 때마다 **날조의 위장 품질이 올라갔다.**
4차에서는 경로 형식으로 잡혔고, 5차에서는 그 형식을 갖춰 나왔다.

**이것이 이번 PoC 의 결론을 확정한다.**
프롬프트에 적은 판별 기준은 그 자체가 모델이 생산할 수 있는 문자열이다.
자기 출력으로 자기를 검증하는 구조는 원리적으로 닫히지 않는다.
**출처 검증은 프롬프트 밖에서, 판단이 개입하지 않는 대조로만 가능하다** —
`source_path` 목록을 KB 에 실제로 적재된 파일 목록과 맞춰 보는 것.

### 결함 2 — 근거 절이 날조에 「확인」 도장을 찍었다

a0d4efe 의 의도는 "경로가 없거나 형식이 아니면 「출처 미확인」" 이었다.
경로 형식이 맞으니 7건 모두 **「확인」** 으로 표기됐다.

    > 상법 제341조의2(자기주식의 취득) 제1항 제5호에 따라 …

**근거 표시 기능은 작동했고, 작동한 결과 날조가 더 그럴듯해졌다.**
읽는 사람은 파일명과 원문 인용과 「확인」 표기를 보고 근거가 있다고 판단한다.
JSON 을 뒤질 때보다 판별이 **어려워졌다.**
이 기능은 유지하되, 「확인」의 의미를 "형식이 맞다"로 낮춰 적거나
기계 대조를 통과한 건에만 붙여야 한다.

### 결함 3 — 06F: 14개 중 3개. 그리고 거짓 오류 사유

    "matched_task_count": 13,
    "executed_task_ids": [ …14개… ],

     … 실행 후 모든 태스크를 primary_tasks 에서 제거하고, 결과를 primary_results 에 추가합니다."

**미래형이다. 실행 대신 실행 계획을 냈다.** 10번 노드가 조사 계획을 냈던 것과 같은 형태다.

보고서 「(현황) 정책·제도」는 문단 4개가 전부 날조인데,
정책 KB 5건은 하나도 쓰이지 않았다. 빠진 것들이다.

**날조가 공백을 채운 것이 아니라 진짜 자료를 밀어냈다.**

### 도입 — `verify_sources.py`

`05_runtime/AIR_MAPPING/verify_sources.py` 로 넣었다.

    python verify_sources.py --kb <KB패키지_디렉터리> --run <실행출력.txt>

KB 패키지의 소스별 하위 폴더를 훑어 파일 목록을 만들고,
실행 출력의 `source_path` 를 파일명으로 대조한다. 없으면 **KB 에 없음**,
있는데 소속이 다르면 **소속불일치**. 없는 출처가 하나라도 있으면 종료 코드 1.

**이 검사는 프롬프트 밖에 있다.** 모델이 출력으로 통과시킬 수 없는 유일한 지점이고,
KB 가 바뀌어도 목록만 다시 주면 된다.
PoC 보고서의 「판단이 개입하지 않는 형식 검증이 필요하다」는 결론이 여기서 실물이 된다.

## 5차 수정 — 노드가 자기 KB 를 먼저 보게 한다 (13개 노드)

### 먼저, 내가 놓친 것 — 06E · 06F 에 태스크 상한이 남아 있었다

    06E POLICY PRIMARY   Process up to 2 tasks satisfying:
    06F NEWS PRIMARY     Process up to 2 tasks satisfying:

2차 수정(6415fc4)에서 `Process at most 1 task` → `Process EVERY task` 로 7곳을 바꿨다.
**이 두 노드는 문구가 달라서(`up to 2 tasks`) 치환에 걸리지 않았고, 당시 노드별 확인이
도구 이름 블록만 봤기 때문에 통과했다.**

**06F 가 14개 중 3개만 한 것은 회피가 아니라 상한을 지킨 것이다.**
프롬프트가 2개까지 하라고 했고 3개를 했다.
「06F 분할이 필요하다」고 적었던 직전 진단은 성급했다 — 상한을 먼저 없애고 다시 재야 한다.

남은 `ONE TASK = AT MOST ONE KB CALL` 은 **태스크당 호출 상한**이지 태스크 수 상한이 아니다.
이것은 의도된 것이라 유지한다.

### 수정 1 — 선행 인벤토리 (조회 노드 9개)

배정 태스크 실행 **전에** KB 를 한 번 넓게 부른다. 질의어는 태스크의 좁은 검색어가 아니라
`must_preserve_themes` 의 주제어다. 돌아온 파일명을 `kb_inventory` 에 적는다.

    "kb_inventory": [
      {"source": "mri_policy",
       "files_seen": ["260227 (보도참고) 디폴트옵션 활용(퇴직연금복지과).pdf", …],
       "unused": [{"source_path": "…", "gist": "디폴트옵션 적립금 53.3조원·가입자 734만명"}]}
    ]

노드마다 자기 항목 하나를 **추가**한다. 남의 항목을 지우지 않는다.
`files_seen` 은 KB 전체 목록이 아니라 **이번 호출에서 본 것**이라고 못박았다 —
의미검색은 상위 몇 건만 돌려주므로 전수 목록을 약속하면 그 자체가 거짓이 된다.

**KB 내용을 프롬프트에 적지 않는다.** 이전에 검토했다가 접은 방식이다
("현실에서는 KB 안에 뭐가 있는지 알 수가 없다"). 노드가 직접 보게 한다.

### 수정 2 — 인용은 본 것 안에서만 (조회 노드 9개)

`source_path` 의 파일명이 `files_seen` 에 없으면 그 레코드를 낼 수 없다.
태스크 실행 중 **도구가** 새 파일을 주면 추가하고 쓴다. **떠올린 이름은 추가하지 않는다.**

경로 형식은 근거가 되지 않는다고 명시했다 —
**직전 날조 7건은 `documents/upload/kb-` 로 시작했고 KB ID 까지 맞았다.**
형식은 지어낼 수 있지만, 본 적 없는 파일명이 자기가 방금 적은 목록에 있을 수는 없다.

### 수정 3 — `unused` 로 진짜 자료를 끌어올린다 (9개 + 07)

인벤토리에 있는데 어떤 배정 태스크도 겨냥하지 않은 자료를 `unused` 에 담아 넘긴다.
**07 이 이것을 근거로 채택할 수 있게 했다** — `supporting_task_ids` 는 빈 배열,
`limitations` 에 "배정 태스크 없이 조회된 자료", `gist` 뿐이면 `PARTIAL` 까지만.

**이것이 5차 실행에서 사장된 자료가 보고서로 올라오는 경로다.**
디폴트옵션 53.3조원·734만명, 기금형 노사정 합의, 로보어드바이저 일임이 여기로 들어왔어야 했다.

### 수정 4 — 07 이 출처를 조회 기록과 대조한다

근거의 `source_paths` 파일명을 그 소스의 `files_seen` 과 맞춘다.
없으면 **VERIFIED 불가**, `DATA_GAP` 으로 내리고 `limitations` 에 "조회 기록에 없는 출처".
해당 소스의 `kb_inventory` 항목 자체가 없으면 대조 불가이므로 `PARTIAL` 까지만.

`verify_sources.py` 의 프롬프트 판이다. 프롬프트 안에 있으니 모델이 통과시킬 수 있지만,
**"방금 적은 목록과 맞춰라"는 자기 출력 안에서 모순이 드러나는 형태**라
"형식을 갖춰라"보다 회피 비용이 높다. 기계 대조는 별도로 계속 돈다.

### 수정 5 — 못 한 것을 다른 말로 적지 않는다 (조회 노드 9개)

- **도구가 이 노드에서 한 번이라도 답했으면 그 뒤의 미실행을 도구 오류로 적을 수 없다.**
  `RETRIEVAL_ERROR` 는 도구가 실제로 실패했을 때만.
- **미래형 금지.** 「…를 순차 실행합니다」는 실행이 아니다.
  출력에 레코드가 없으면 안 한 것이다.
- `matched_task_count` 와 `executed_task_ids` 의 개수는 반드시 같다.

### 규칙 충돌 처리

`ONE-CALL RULE` 의 "No second search to improve recall" 이 인벤토리 호출을 막을 수 있어,
**그 자리에** 예외를 명시했다. 총 호출 수 = **1 + 배정 태스크 수**,
배정 0건이면 인벤토리도 하지 않는다(SOURCE GATE 의 ZERO KB calls 우선).

지금까지 여섯 번 중 다섯 번이 **새 규칙과 기존 문장의 충돌**에서 나왔다.
새 규칙을 넣을 때 충돌하는 자리를 같이 고치지 않으면 모델은 둘 중 하나를 따르고,
어느 쪽을 따를지 예측할 수 없다.

|---|---|

### KB 상태 — 파일은 정상, 구조가 검색을 방해한다

사용자 화면 확인 결과 KB 는 모두 정상 적재돼 있다. 못 읽은 것이 아니다.

1. **뉴스 KB 에 S02·S04·S06 이 혼재** — 40~50건 중 S06 은 20건.

   **이슈별 분리는 하지 않기로 했다** — 실제 뉴스 KB 는 원래 섞여 있고,
   그 안에서 찾아내는 것이 시스템의 일이다. 분리하면 시험이 쉬워지고 결과가 현실을 못 보여준다.
2. **S06 정책 카드(01–05)가 뉴스 KB 에 들어가 있다** — 사용자가 정책 KB 로 옮기기로 함.
3. **parent–child 청킹이 카드를 섹션별로 쪼갠다** —
   `[KB DOCUMENT]` · `[KEY EVIDENCE]` · `[ASSET-MANAGEMENT IMPLICATION]` · `[SEARCH KEYWORDS]` 가
   각각 다른 청크다. **근거가 든 청크에는 회사명이 없고, 키워드가 든 청크에는 수치가 없다.**
   6차에 3건, 7차에 0건으로 흔들린 이유다.

### 7차 수정 — 세 곳

**수정 1 — KB 가 알려준 축으로 1회 재질의 (조회 노드 9개)**

`ONE-CALL RULE` 의 예외를 둘로 늘렸다. 예외 2 의 판단 기준은 하나다.

- KB 응답에 **그 소스가 실제로 가진 항목·필드·주제**가 적혀 있다 → **재질의한다.**
  새 질의어는 **KB 가 쓴 말 그대로**. 지어낸 동의어가 아니다.
- 그냥 "없다"로 끝났다 → 재질의하지 않는다. `NO_RESULT` 다.

recall 재검색도, 같은 질문 되풀이도 아니다. **질문을 KB 의 축으로 옮기는 것이고 태스크당 1회다.**
총 호출 = **1(인벤토리) + 태스크 수 + 재질의(태스크당 최대 1)**.
재질의한 태스크는 `requery` 필드에 계기와 새 질의어를 남긴다.

**수정 2 — 제도 이름으로 상품 데이터베이스를 묻지 않는다 (05)**

상품·통계 소스는 상품 속성으로 색인된다 — 회사명·대유형·자산유형·세제구분·설정액·순위·기준일.
제도 이름(퇴직연금·DC·IRP)은 그 필드가 아닐 수 있다.

- 소스 표기 회사명은 반드시 넣는다(기존 ALIAS 규칙).
- **그 소스가 가질 법한 축을 함께 넣는다.**
- **제도명만으로 이루어진 질의는 만들지 않는다.**
- 뉴스·정책은 반대다. 거기서는 제도 이름이 본문의 말이다.

KB 내용을 프롬프트에 적지 않았다. **축을 넓게 잡아 첫 질의가 빗나갈 확률을 줄일 뿐이고,
빗나가면 수정 1 이 받는다.**

**수정 3 — 당사 자료는 버릴 수 없다 (07)**

`unused` 에 당사 회사명이 든 항목이 하나라도 있으면 **반드시 근거로 만든다.**
`company_status_snapshot` 이 비었는데 `unused` 에 당사 자료가 있으면 **그것은 누락이다.**

7차에서 06D 가 FreeSIS 자료를 `unused` 로 정확히 넘겼는데 **07 이 쓰지 않아
`evidence_items` 가 빈 배열로 나왔다.** 6차 수정의 채택 규칙이 너무 물렀다.

### 다음 실행에서 볼 것

1. **`requery` 가 나오는가.** FreeSIS 가 「순위·점유율·자산유형별 운용규모」로 다시 묻는가
2. **당사 현황 블록에 실제 숫자가 들어가는가** — 설정규모 순위, ETF 설정액
3. 05 의 당사 태스크 `query_terms` 에 제도명만 남아 있지 않은가
4. 뉴스 조회가 0건을 벗어나는가 (혼재 상태 그대로, 정책 카드만 이동)
5. **날조 0건이 유지되는가** — 이것이 회귀하면 수정 1·2 를 되돌린다

### 중단 — 에이전트 1 과 **같은 값**의 체크섬 오류

### 원인 — 도구가 주지 않는 것을 스키마가 요구했다

playground 로그에 남은 **KB 도구 원본 출력 17건을 전부 봤다.** 전부 이 모양이다.

    { "answer": "<검색 결과를 풀어 쓴 글>", "contents": [] }

- **`contents` 는 17건 모두 비어 있었다.** 이 도구는 문서 배열을 돌려주지 않는다.
- 파일명은 `answer` 끝에 꼬리로 **붙을 때만** 온다. **17건 중 6건.**

      ---
      출처:

- 지금까지 **모든 실행을 통틀어** 산출물에 나온 진짜 파일명은 정확히 5개이고,
  그 5개는 전부 이 꼬리 줄에 찍혔던 것들이다.
  `08_주식보상…` · `09_삼성운용…` · `20_RSU관리…` ·
  `FREESIS_MARKET_SUMMARY_MARKED.txt` · `FREESIS_MAJOR_COMPANY_MARKED.txt`.

**여덟 번의 회피 모양이 전부 여기서 나온다.**
`files_seen`·`source_path` 는 도구가 주지 않는 값이다. 스키마는 그 칸을 요구했다.
칸을 비우는 것은 계약 위반처럼 보이고, 채우는 방법은 지어내는 것뿐이다.

**있지도 않은 데이터를 요구한 스키마의 문제**다.

### 8차 수정 — 스키마를 도구의 실제 출력 모양에 맞춘다 (노드 14개)

**수정 1 — `kb_inventory`·`files_seen` 을 없앴다 (조회 노드 9개)**

파일 목록을 적는 칸이 사라졌다. 도구가 목록을 주지 않으므로 **지어내야만 채울 수 있는 칸**이었다.

**수정 2 — 레코드마다 옮겨 적는 칸 두 개 (조회 노드 9개)**

    "answer_excerpt": "<이 사실이 나온 문장을 `answer` 에서 그대로 복사>",
    "source_footer":  "<`- Source: …` 줄 그대로 복사. 꼬리가 없으면 \"\">"

- `answer_excerpt` 가 `answer` 에 없는 문장이면 그 레코드는 조회 결과가 아니다.
- **`source_footer` 가 `""` 인 것이 정상이다.** 17건 중 11건이 그랬다.
  07 이 「<소스 ID> KB 검색결과」로 싣는다. **파일명 없이도 근거가 된다.**
- `source_path` 는 꼬리에서만 만든다. 꼬리가 없으면 `null` 이다.

**수정 3 — `unused` 를 `kb_other_points` 로 (조회 노드 9개 + 수집 3개 + 07)**

배정 태스크 전에 KB 를 한 번 넓게 부르는 것은 그대로 둔다. 그 결과를 **파일명이 아니라 문장으로** 적는다.

    "kb_other_points": [{"point": "<answer 에서 그대로 복사>", "source_footer": "<꼬리 또는 \"\">"}]

7차에 `unused` 로 들어와 보고서에 실렸어야 했던 디폴트옵션 53.3조원·734만명은
이 경로로 그대로 들어온다. **파일명을 경유하지 않을 뿐이다.**

**수정 4 — 07 의 출처 판정 기준 교체**

`documents/upload/kb-` 로 시작하는지 보는 형식 검사와 `files_seen` 대조를 **둘 다 버렸다.**
둘 다 모델이 생산할 수 있는 문자열이었고 8차에 36건이 그 검사를 통과했다.
이제 출처는 `source_footer` 에서만 나온다. 꼬리가 없으면 `PARTIAL` 까지 허용하고 버리지 않는다.

**수정 5 — 10 의 근거 절**

`source_names` 가 「<소스 ID> KB 검색결과」면 **그대로 쓴다. 출처 미확인이 아니다.**

    **[E05]** 부분확인 · `mri_news KB 검색결과`
    > <도구가 돌려준 문장 그대로>

### `verify_sources.py` 보강

- 폴더 이름을 `mri_news@94eaa5b2` 로 적으면 **KB ID 로도 판정한다.**

- 파일 목록을 주지 않은 소스의 인용은 **"판정불가"로 따로 센다.** 없다고 단정하지 않는다.

### 다음 실행에서 볼 것

## 9차 실행 보충 — 「도구 이름 오류 연쇄」는 플랫폼 고장이 아니었다

앞 절에서 9·10차를 묶어 적으면서 9차의 도구 오류를 따로 파고들지 않았다. 그것이 본체였다.

### 기계 대조 — 날조 0건

    인용된 출처 3건 — 일치 3 · 소속불일치 0 · KB 에 없음 0
    판정: 인용된 출처가 모두 KB 에 있다.

**지금까지 유일하게 깨끗한 실행이다.** 06F 의 넓은 조회가 꼬리 줄로 진짜 파일 3건을 돌려줬고
(`08_주식보상…` · `20_RSU관리…` · `07_신한_워크플레이스WM…`), 노드는 그것을 그대로 옮겨 적었다.
**도구가 파일명을 주면 모델은 베낀다. 안 주면 지어낸다.** 8차 수정의 근거가 여기서 한 번 더 확인됐다.

### 연쇄의 정체 — 노드마다 바로 앞 노드의 도구를 불렀다

오류 메시지를 짝지어 보면 한 칸씩 밀려 있다.

    06F 차례 끝 → 06A 가 94eaa5b2(06F 것) 호출 → "try 39372306"  ← 06A 자기 도구
    06A 차례 끝 → 06C 가 39372306(06A 것) 호출 → "try f01bb5d9"  ← 06C 자기 도구
    06C 차례 끝 → 06D 가 f01bb5d9(06C 것) 호출 → "try cf938211"  ← 06D 자기 도구
    06D 차례 끝 → …  → 06B 가 cf938211(06D 것) 호출 → "try 2831d472" ← 06B 자기 도구
    06B 차례 끝 → 06D2 가 2831d472(06B 것) 호출 → "try cf938211" ← 06D2 자기 도구

**플랫폼은 매번 정답을 알려 줬다.** 오류 메시지가 가리킨 도구는 항상 그 노드 자신의 것이었다.
「circular tool name suggestions」도, 「system-level tool routing failure」도 아니다.
9차의 06F 가 `error_detail` 에 그렇게 적었고 **틀렸다.**

### 원인 — 내 규칙이 재시도를 다음 노드로 밀어냈다

2차 수정에 넣은 문장이다.

    - 오류가 알려준 이름으로 **즉시 다시 부른다.**

모델은 이 문장을 읽고 「도구 이름 오류 발생 — 즉시 재시도」라고 **적은 뒤 차례를 끝냈다.**
슈퍼바이저는 그것을 노드 완료로 보고 다음 노드로 넘겼다. 재시도는 도구 주인이 아닌
다음 노드에서 일어났고, 그 노드는 앞 노드의 도구 이름을 물려받아 또 틀렸다. 한 칸씩 영원히.

결과: 뉴스 노드가 15개 태스크 중 **1개만 실행**하고 14개를 `RETRIEVAL_ERROR` 로 냈다.
ZeroIn 3개 소스는 한 번도 자기 도구를 부르지 못했다.
**10차에서 ZeroIn 이 전부 `SOURCE_NOT_EXECUTED` 로 나온 것도 같은 뿌리다.**

### 10차 수정 — 재시도는 말이 아니라 호출이다 (조회 노드 9개)

- 오류가 알려준 이름은 **네 도구다.** 네 차례에 뜬 오류이기 때문이다.
- 그 이름으로 **같은 차례 안에서 곧바로 호출한다.**
- **재시도하겠다고 적고 차례를 끝내지 않는다 — HARD RULE.** 위 연쇄를 프롬프트에 그대로 실었다.
- 이것을 「순환 오류」·「시스템 라우팅 실패」로 적지 않는다. 9차가 그렇게 적었고 틀렸다.

이 수정과 8차(꼬리 복사)·9차(할 일 없을 때 보고서 금지)가 한 번도 함께 돌아 본 적이 없다.
다음 실행이 셋의 첫 시험이다.

마지막 실행에서 S05·S07 이 `status: "CORRECTABLE"` · `corrections: []` 로 나왔다.

03X 프롬프트 전체에서 `corrections` 는 **스키마 예시의 `[]` 로 딱 한 번** 나온다.
02 에서 받아 넘기라는 규칙도, 정합성 검사도 없다. **스키마의 `[]` 를 그대로 베낀 것**이고,
`must_preserve_themes: []` 와 같은 모양이다. 로그에 이미 여섯 번 기록된 실패다.

02 쪽에도 구멍이 있다. 판정 매핑이 `WARN → CORRECTABLE` 인데, WARN 이 떠도 구체적 수정안이
안 나올 수 있다. 그러면 CORRECTABLE 인데 corrections 가 빈다.

고칠 곳은 둘이다 — 03X 에 「02 의 corrections 를 그대로 옮긴다, CORRECTABLE 인데 비면 오류다」,
02 에 「corrections 가 비면 CORRECTABLE 이 아니라 PASS 다. WARN 사유는 checks 에 남긴다」.
**사람이 판정을 검토할 때 걸리는 문제이고 산출물의 사실 정확도는 바꾸지 않아서 뒤로 미뤘다.**

## 에이전트1 02 — `corrections` 가 빈 `CORRECTABLE` 을 금지했다

### 진단을 고친다 — 03X 가 아니라 02 였다

앞 절에서 이 문제를 「03X 가 스키마의 `[]` 를 베낀 것」으로 적었다. **틀렸다. 확인하지 않고 짐작했다.**

로그를 뒤지니 9/14 08:58 실행에 corrections 가 실제로 붙은 CORRECTABLE 이 하나 있었고,
**02 와 03X 양쪽에 글자까지 같은 내용으로 나온다.**

    02   "corrections": [{ "field": "key_changes[2]",
                           "from": "퇴직연금 적립금 500조원 돌파",
                           "reason": "CURRENT_MRI에 '2025년 말 기준 …' 으로 명시되어 시점 정보 추가 필요" }]
    03X  "corrections": [{ 같은 내용 그대로 }]

**03X 의 전달은 정상이다.** 02 가 주면 03X 는 넘긴다.
따라서 S05·S07 의 빈 배열은 **02 가 CORRECTABLE 을 내면서 corrections 를 비운 것**이다.

### 수정 — 02 한 노드, 두 자리

02 의 CORRECTABLE 정의는 이미 「one or more limited source-grounded corrections are required」다.
`corrections: []` 인 CORRECTABLE 은 **02 자신의 계약에 없는 값**이다.
새 규칙을 만든 것이 아니라 이미 있는 규칙이 지켜지지 않았다 — 아홉 번째 같은 모양이다.

**1) 판정 매핑에 조건을 붙였다.**

    - WARN **and** a concrete source-grounded correction exists → CORRECTABLE
    - WARN but nothing concrete to correct → PASS (WARN 사유는 checks 에 남긴다)

**2) 강제 선택을 넣었다. 자기 점검 한 줄이 아니라 도망갈 곳을 막는 쪽이다.**

이 프로젝트에서 이미 확인된 것 — **자기 점검 필드는 자기가 만든 것을 못 잡는다**
(06 의 `records_derived_only_from_tool_output` 이 그렇게 실패했다).
그래서 「확인하라」가 아니라 「둘 중 하나를 골라라, 세 번째는 없다」로 적었다.

    (A) corrections 에 항목이 최소 하나 있고 validated_issue 에 반영됨 → CORRECTABLE
    (B) 구체적 수정안을 만들 수 없음 → PASS, 그 WARN 은 checks 에 status·reason 으로 남긴다

(B) 는 축소가 아니다. **걸린 것은 `checks` 에 다 남고, 그것이 사람이 읽을 자리다.**
상태 칸에 근거 없는 경고를 남기는 쪽이 축소다.
`FINAL CHECK` 에도 한 줄 더했다(강제 선택이 본체이고 이쪽은 보조다).

10,998 → 12,143자. **노드 9 / 엣지 9 그대로.**

### 영향 범위 — 라벨 하나다. 판정은 안 바뀐다

어제 이 수정을 「에이전트1 판정 거동을 건드리는 첫 수정」이라고 적었다. **과장이었다.**

- **03 의 판정 규칙은 `validation_status` 를 `FAIL` 에서만 본다.**
  OPPORTUNITY / MONITOR / EXCLUDE 는 렌즈 점수가 정한다.
  CORRECTABLE 이 PASS 로 바뀌어도 이 분기에 걸리지 않는다.
- **에이전트2 33개 노드 중 `fidelity.status` 로 분기하는 노드가 없다.**
  `fidelity` 를 읽는 04·07·10 은 전부 `must_preserve_themes` 를 가져가려고 읽는다.
  04 의 `"status": "PASS|CORRECTABLE"` 은 스키마 예시일 뿐이다.
- **03 의 17번(「Do NOT change it to PASS」)과 충돌하지 않는다.**
  그것은 03 이 02 의 값을 바꾸지 말라는 규칙이고, 02 가 스스로 판정하는 것과 무관하다.

바뀌는 것은 셋뿐이고 전부 표기다 — 02 요약의 `pass_count`/`correctable_count`,
검토서 「원문 정합성」 줄, 핸드오프 `fidelity.status`.

**03X 에는 아무것도 넣지 않았다.** 제대로 동작하는 노드에 예비 규칙을 얹지 않는다.

## 13차 — 도구 호출 0회, 그런데 보고서는 완결되었다

    RETRIEVAL_ERROR: (0건)

## 15차 수정 ⑤ — 「실행합니다」를 실행으로 세지 않는다

조회 노드 9개에 절 두 개를 넣었다. 노드당 +1,788자.

### 「실행은 말이 아니라 호출이다」

9차 수정의 「재시도는 말이 아니라 호출이다」는 **오류가 난 뒤**에만 걸려 있었다.
15차는 오류가 나기 전, 최초 실행에서 같은 방식으로 무너졌다. 규칙을 그 앞으로 옮긴다.

15차 06F2 의 실제 출력을 그대로 인용해 넣고, 세 가지를 금지했다.

1. **의도를 적는 필드를 만들지 않는다** — `execution_note`·`plan`·`next_step`.
   「이제 무엇을 하겠다」를 적는 칸은 하지 않은 일을 한 것처럼 보이게 하는 서식이다.
2. **`stage_status` 에 `EXECUTION_STARTED` 를 쓰지 않는다.** 시작은 상태가 아니다.
   차례가 끝나는 순간 실행은 끝났거나 안 한 것이고, 그 둘뿐이다.
3. **출력 직전 마지막 점검** — `matched_task_count > 0` 인데 이번 차례에 도구를
   한 번도 부르지 않았으면 그 차례는 실패다. 출력하지 말고 지금 부른다.

### 「부른 결과는 네 출력에 담는다」

15차의 오귀속 경로를 양쪽에서 막는다.

- 부른 노드: 결과를 자기 `primary_results`/`followup_results` 에 담는다.
  **부르고 안 담는 것은 부르지 않은 것보다 나쁘다** — 내용이 사라지지 않고
  엉뚱한 자료원 이름을 달고 살아남는다.
- 받은 노드: **네가 부르지 않은 답변을 `kb_other_points` 에 담지 않는다.**
  대화에 남은 다른 노드의 조회 결과는 네 것이 아니다.

06F 가 결과를 담았으면 06A 가 주울 것이 없고, 06A 가 안 주우면 07 이
뉴스 기사를 「제로인 자료원 검색결과」로 적을 일이 없다. 어느 한쪽만 막아도 끊긴다.

    If RT01 is: RETRIEVAL_ERROR / NO_RESULT / missing

    {{...}} 없음                      → 이미 실행 가능. depends_on 을 비우고 넘긴다
    {{...}} 있고 부모 SUCCESS/PARTIAL → 실제 값으로 치환
    {{...}} 있고 부모 NO_RESULT/ERROR → 그 태스크만 unresolved

### 2. 새 실패 모드 — 06B 가 노드가 아니라 챗봇이 됐다

> I've reviewed the comprehensive research synthesis...

뒤 노드는 그것을 「지금 이 대화에서 벌어지는 일」로 읽는다.

### 측정

조회 노드 1개 = **27개 섹션 · 21,500자**. 9개 합계 **189,093자**.

같은 말을 하는 섹션이 몇 개인지 세 보았다.

| 계열 | 섹션 수 |
|---|---|
| 「반드시 도구를 불러라」 | **9개** (KB CALL REQUIRED · NO_RESULT REQUIRES AN ACTUAL KB CALL · ACTUAL-KB-CALL PROOF · KB 도구 호출 · 실행은 말이 아니라 호출이다 · 부른 결과는 네 출력에 담는다 · 배정 태스크 전에 한 번 넓게 부른다 · ABSOLUTE EXECUTION CONTRACT · ONE-CALL RULE) |

### 진단

13차부터 18차까지 실패할 때마다 섹션이 하나씩 붙었다. 붙일 때마다
앞의 섹션들이 덜 읽혔다. **실패 모드가 매번 바뀐 이유가 이것이다** —
버그가 여러 개인 게 아니라, 21,500자 안에서 매번 다른 규칙이 떨어져 나갔다.

들었던 수정은 둘뿐이고 둘 다 규칙이 아니라 **구조**를 바꿨다.

- 8차: `files_seen` 칸을 **없앴다** → 날조 36건 → 0건
- ⑦: `my_kb_tool` 칸을 **만들었다** → 도구 이름 오류 0건

「기준선이 나올 때까지 감량을 미룬다」는 방침은 폐기한다.
13~18차 여섯 번 연속 깨끗한 실행이 없었다. 기준선이 아직 안 나온 것이 아니라,
**이 분량에서는 안 나온다**는 것이 여섯 번의 결과다.

### 조치 — `build_prompts.py`

AIR Studio 에는 공유 프롬프트가 없다. 그래서 골격을 **파일 하나**에 두고
9개를 찍어낸다. 앞으로 규칙 수정은 골격 한 곳만 고치고 재생성한다.
9벌이 따로 드리프트하지 않는다.

워크플로 전체 251,648 → 101,206자.

남긴 것 (실행으로 증명된 것만):

1. 도구 목록을 먼저 적는다 (`my_kb_tool`) — ⑦, 18차 증명
2. 먼저 세고 센 만큼 부른다 + 장부 (`source_task_ledger`)
3. 미실행과 자료 없음은 다르다 (NO_RESULT 는 완수)
4. 도구가 돌려주는 것 (`answer_excerpt` · `source_footer` 는 옮겨 적는 칸)
5. **출력은 JSON 하나뿐이다 — ⑨ 신규**
6. 네 것만 건드린다 (pass-through + 금지 필드 목록)
7. 도구 실패 처리

버린 것:

- 중복 섹션 20개
- `retrieval_proof` (②) — 자기 점검 필드는 자기가 지어낸 것을 잡지 못한다

  18차에 06D 가 낸 「4.0조 → 19.0조」는 프롬프트가 보여 준 실패담의 형식과 닮았다
- **「배정 태스크 전에 한 번 넓게 부른다」** — 호출 수 계산을 `1 + 태스크 수` 로

  19차에 조회 누락이 보이면 되살린다

핵심은 마지막 줄이다. 앞의 금지 네 줄은 이 프로젝트에서 계속 안 들었다.

답을 태스크에서 빼니 살을 붙이지 않았다. 그 부분은 맞았다.

**그러나 10번 검수 블록은 더 나빠졌다.**

    자료원별 근거: 정책 0 · 뉴스 0 · 제로인 0 · 협회통계 0 · MRI 원문 13

19차 12건 → 20차 **13건**. 전사는 그대로다.

남은 새는 곳은 **RQ 질문문 자체**다. 04 가 이렇게 썼다.

    "question": "... RSU 도입률이 현재 0.6%에서 선진국 수준(15-65%)으로
                 성장할 가능성과 시간 프레임은?"

**질문 안에 답이 들어 있다.** 그리고 `research_questions` 배열은 조회 노드가
그대로 통과시켜야 하는 상태 필드다. 태스크에서 빼도 질문에 남아 있으면 소용이 없다.

### 2. ⑪은 실행조차 되지 않았다 — 06X 가 06R1 이 됐다

06X 출력이 의존성 해소가 아니었다. `research_question_id: "S06-RQ02"` 짜리
**RQ별 collector** 였다. 바로 앞 노드 06R1 의 출력 형태를 그대로 복제하고
RQ 번호만 하나 올렸다.

그리고 그 뒤로 여덟 노드가 같은 일을 했다.

| 노드 | 원래 역할 | 20차에 한 일 |
|---|---|---|
| 06R1 | 1차 결과 수집 | RQ01 collector (정상) |
| **06X** | **의존성 해소** | **RQ02 collector** |
| 06B | 제로인 상세 조회 | RQ03 collector |
| 06D2 | FreeSIS 2차 조회 | RQ04 collector |
| 06R2 | 조회 결과 수집 | RQ05 collector |
| 06S | 신호 검토 | RQ06 collector |
| 06T | 후속 계획 | RQ07 collector |
| 06E2 | 정책 보충 조회 | RQ08 collector |
| 06F2 | 뉴스 보충 조회 | 전체 종합 |

**RQ01 → RQ02 → … → RQ08.** 빠짐없이, 순서대로, 정확하게.

이것이 19차보다 중요한 발견이다. 역할 붕괴가 무작위가 아니라 **완벽하게 규칙적**이다.
앞 노드의 출력이 뒤 노드에게 **예시(few-shot example)** 가 되고,
뒤 노드는 그 패턴을 이어받아 파라미터만 증가시킨다.

이건 고장이 아니다. **LLM 이 맥락을 읽는 정상 동작이다.**

### 3. ⑧은 아무도 적용하지 않았다

S06-T15 는 이번에도 죽었다. 그런데 막은 것이 06X 가 아니다.
06X 가 collector 가 돼 버리자 **06D(FreeSIS)** 가 대신 판정했다.

    "unresolved_dependent_tasks": [
      { "task_id": "S06-T15", "reason": "DEPENDENCY_FAILED",
        "detail": "S06-T14 returned NO_RESULT" }

T15 의 `query_terms` 는 「NH-Amundi운용 · 퇴직연금 · 설정액 · 수익률 · 운용성과」로
`{{...}}` 가 없다. ⑧대로면 실행 가능하다. 그런데 **⑧은 06X 에만 있고, 06D 에는 없다.**
규칙을 가진 노드가 역할을 잃으면 규칙도 함께 사라진다.

제로인 상세는 20회 중 **한 번도** 불리지 않았다.

### 4. 조회 계층 — my_kb_tool 은 5/5 정확, 장부는 또 틀렸다

역할을 지킨 다섯 노드는 전부 정확한 KB ID 를 적었다
(`66cbc0fb` · `94eaa5b2` · `39372306` · `f01bb5d9` · `cf938211`). ⑦은 견고하다.

그러나 장부는 또 틀렸다.

| 노드 | matched_task_count | executed_task_ids | all_my_tasks_done |
|---|---|---|---|
| 06E 정책 | 4 | **5개** | true |
| 06F 뉴스 | 13 | **14개** | true |

프롬프트에 「개수가 다르면 끝난 것이 아니다」를 써 두었고 두 노드 다 통과시켰다.
**자기 점검 필드는 세 번 연속(18·19·20차) 자기 위반을 잡지 못했다.**

### 5. 하류 검증 계층은 두 번 연속 작동했다

19차와 20차 모두 07 이 근거 전량을 `MRI 원문` 으로 분류했고,
10 이 「정책 0 · 뉴스 0 · 제로인 0 · 협회통계 0」이라고 신고했다.

**조회 계층이 거짓말을 했고, 뒤가 매번 잡아냈다.**

## 최종 결론 — 20회의 결과

### 원인 (확정)

**23단계 단일 체인에서 앞 노드의 출력은 뒤 노드에게 예시가 된다.**

20차가 이것을 교과서적으로 보여줬다. 06R1 이 RQ01 collector 를 내자
뒤따르는 여덟 노드가 RQ02~RQ08 을 이어받았다. 무작위 고장이라면
이렇게 규칙적일 수 없다.

같은 기제가 20회 내내 층을 바꿔 가며 반복됐다.

| 옮겨간 것 | 언제 |
|---|---|
| 파일명 | ~8차 (`files_seen` 삭제로 차단) |
| 도구 이름 | 14·17차 (⑦ `my_kb_tool` 로 차단) |
| 역할(대화체) | 18차 (⑨로 차단) |
| 역할(직무) | 19·20차 — **차단 실패** |
| MRI 문장 | 19·20차 — **차단 실패** |

앞의 셋은 **필드를 없애거나 만들어서** 막았다. 뒤의 둘은 막지 못했다.
없앨 필드가 없기 때문이다. 오염원이 필드가 아니라 **맥락 그 자체**다.

### 이것은 프롬프트로 고칠 수 없다

노드 간 맥락 격리는 플랫폼의 몫이고, AIR Studio 에서는 불가능하다(확인됨).
프롬프트는 189,093자에서 38,651자까지 줄여 봤고, 규칙을 열한 번 고쳐 봤다.
**들었던 것은 전부 구조 변경이었고, 규칙 추가는 한 번도 듣지 않았다.**

### 그래서 PoC 의 결론은 이것이다

이 PoC 가 실증한 것은 「AI 가 자료 조회를 자동화한다」가 아니다.

**「AI 가 조회하지 않고 지어낼 때, 그것을 기계적으로 검출할 수 있다」**

- 07·10 의 출처 판정 계층이 19·20차 연속으로 날조를 전량 적발했다
- 대조 도구(`verify_sources.py`)가 모델이 통과시킬 수 없는 5개 검사로
  12~18차의 이상을 잡아냈다
- 20회의 실행 기록이 실패 모드를 층별로 분류할 수 있을 만큼 남았다

「완벽히 돌아간다」보다 **「무엇이 안 되는지 기계가 잡아낸다」**가
PoC 로서 더 정직하고, 실무 도입 판단에 더 쓸모 있다.

### 다음 구조를 만든다면

1. **단계를 줄인다** — 23 → 5~7. 체인이 짧으면 예시가 쌓일 자리가 없다
2. **조회를 한 번에 한 소스씩, 독립 실행으로 분리한다** — 워크플로를 나눈다
3. **RQ 질문문에 MRI 수치를 넣지 않는다** — 04 의 질문은 「무엇을 모르는가」만 적는다
4. **검증은 지금 것을 그대로 쓴다** — 이 층은 작동이 확인됐다
